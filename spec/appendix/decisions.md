# Appendix C. Decision Log

Design decisions made while drafting the specification, with their rationale.
Each entry records who decided: **(user)** means the project owner chose it
explicitly, and **(proposal)** means the spec authors proposed it and it is
open for review.

## Language

| # | Decision | Rationale |
|---|----------|-----------|
| L1 | wowlua is a **strict superset** of Lua 5.1, with no exceptions **(user)** | Existing addons must compile unchanged. This is why casts use `::` and why there are no word operators such as `as` or `is` in expressions. |
| L2 | **Luau/TypeScript-style inline type annotations** **(user)** | Familiar, concise, and parseable without ambiguity in invalid-Lua positions. |
| L3 | **Gradual typing**, default mode `basic` **(user)** | Existing Lua compiles unchanged. Annotated code gets checked. `--!strict` per file. |
| L4 | **Classes with `end` blocks** and a `constructor` keyword. Instances via `Class.new()` or `Class()` **(user)** | Looks like Lua and is explicit. |
| L5 | **import/export modules** **(user)** | No globals, deterministic load order, and room for a typed WoW standard library. |
| L6 | Build info and debug macros come from **compiler-known modules** (`wowlua:meta`, `wowlua:debug`), with **no `$` sigil** **(user)** | One mechanism (modules). Folding works because import bindings are immutable and compiler-known. |
| L7 | **Core decorators are always in scope**. Framework decorators need imports **(user)** | `@` cannot clash with Lua. Core decorators are language features. |
| L8 | **Decorators:** built-in ones are compile-time. User decorators are runtime functions `(target, ctx) -> replacement?`. Field decorators receive `(nil, ctx)` and their return value is ignored (metadata and registration only) **(user, amended in review R1)** | Powerful enough without the complexity of user compile-time macros. Fields have no value at decoration time. |
| L9 | **Reflection opt-in per class** (`@reflect`). Class identity is always available **(user)** | Keeps output small. Identity is cheap and widely needed. |
| L10 | Syntax sugar: compound assignment, `continue`, `?.`, `??`, backtick interpolation, default parameters, record destructuring **(user)** | Common requests from Lua developers. All lower to Lua 5.1. |
| L11 | Lua 5.3-style bitwise operators, `//`, digit separators, binary literals, `const` **(user)** | All lower to WoW's `bit` library or to literals. |
| L12 | **Enums with braces**: `enum E { A, B }` **(user)** | Mirrors the table it compiles to. |
| L13 | Interfaces, generics, abstract classes, type guards **(user)** | |
| L14 | `import a from "x"` (no braces) and `import _ from "x"` for side effects **(proposal)** | `import {a} from "x"` and `import "x"` are valid Lua calls (superset rule L1). |
| L15 | No explicit type arguments at call sites **(proposal)** | `f<T>(x)` is a valid Lua comparison. Inference and expected types cover the need. |
| L16 | Exported bindings are immutable **(proposal)**. Imports are local copies, except bindings that take part in a run-time-only import cycle, which are read lazily from the module table (see L20) | Cheap imports in the common case. |
| L17 | Widget classes lower to Blizzard-style mixins **(proposal)** | Frames already have a metatable, and the mixin pattern is idiomatic WoW. |
| L18 | Extended escapes (`\x`, `\u{}`) only in backtick strings **(proposal)** | `"\x41"` means `"x41"` in Lua 5.1 (superset rule L1). |
| L19 | **`Secret<T>`** models Midnight secret values. Forbidden operations are flagged, and `issecretvalue` / `canaccessvalue` narrow **(user)** | Catches a whole class of Midnight runtime errors at compile time. |

| L20 | **Automatic load order** from imports plus usage analysis of globals and `ns` fields. Edges are classified as load-time or run-time. The order is a topological sort over load-time edges. Cycles of run-time edges only are allowed (lazy bindings). Cycles containing a load-time edge are errors. Unknown callees count as load-time. `build.load-order` overrides **(user, R1)** | Migrated addons keep working, mutual references are possible, and genuine load-time cycles are caught. |
| L21 | Ambiguous ordering (dynamic global names, several writers): warning, and the affected files keep their source order **(user, R1)** | |
| L22 | Core decorator names **always** resolve to the core decorator **(user, R1)** | Predictable. A user function with the same name must be imported under an alias. |
| L23 | Optional calls (`f?.()`, `a?:m()`) yield **exactly one value** **(user, R1)** | Simple, efficient lowering. |
| L24 | Top-level exported functions, classes and enums are **hoisted** (pre-declared at module top) **(user, R1)** | Mutual references between declarations work. |
| L25 | `::` takes a **full type** including `\|` and `&`. A bitwise operator after a cast needs parentheses **(user, R1)** | Reads naturally for union casts. |
| L26 | Registering decorators (`@global`, `@event`, `@slash`, `@hook`, `export`) capture the **final** decorated value. Transforming core decorators (`@profile`, `@trace`, `@if`, `@debugOnly`, `@inline`) apply innermost **(user, R1)** | `@event @memoize` registers the memoized function. |
| L27 | **Type packs** (Luau-style `T...` generic pack parameters) plus intrinsic-checked stdlib APIs **(user, R1)** | `pairs`, `select`, `pcall`, event payloads and constructor forwarding become typeable. |
| L28 | Type-based fast lowerings (no `tostring` in interpolation, `?.` as `and`, `??` as `or`) only in **strict** mode **(user, R1)** | Basic-mode types may be wrong at runtime, so basic mode always uses the safe forms. |
| L29 | No methods outside class bodies (E2003 with a quick fix) **(user, R1)** | Classes are sealed. |
| L30 | `type`/`interface` may be declared anywhere (block-scoped). `class`/`enum` only at module top level **(user, R1)** | |
| L31 | v1 includes **getters/setters, overloads in classes, typed coroutines, `setmetatable` typing** **(user, R1)** | Only classes with properties pay for an `__index` function. |
| L32 | `local addonName, ns = ...` is typed `(string, AddonNamespace)`. `AddonNamespace` is an interface projects extend with `declare interface` (declaration merging) **(user, R1)** | Typed classic namespace sharing. |
| L33 | Top-level `return` is an error in modules and allowed in scripts **(user, R1)** | |
| L34 | Generic variance: covariant in basic mode, invariant for mutable positions in strict mode **(user, R1)** | Pragmatic by default, sound in strict. |

| T23 | Every minification level keeps **at least one line break per statement**, so source maps stay line-based and `wowlua trace` always works **(user, R1)** | WoW error messages have no column numbers. |
| T24 | Bundles **isolate modules**: each runs protected, errors go to `geterrorhandler()`, and later modules still load **(user, R1)** | Same behavior as separate files. |
| T25 | Publish builds go to `dist/targets/<target>/`. Zips get a target suffix when targets differ **(user, R1)** | No collisions between targets. |
| T26 | Module graph and load order are computed **per flavor**. Single-TOC order is a topological sort over all flavors **(user, R1)** | `@if` on imports works. |
| T27 | Top-level `config` defines defaults that profiles override (deep merge for objects, replacement for arrays) **(user, R1)** | |
| T28 | Output layout: user code under `src/`, generated code under `wowlua/`, libraries under `libs/` **(user, R1)** | No collisions with user folders. |
| T29 | `wowlua:meta` in libraries: `addon`, `build`, `flavor` from the consuming addon; `features`, `config` are the library's own. Libraries support all flavors unless declared otherwise **(user, R1)** | |
| T30 | Resolution over the **union** of features, flavors and dev-dependencies, with one version per package across the workspace where possible. Lock entries record their users **(user, R1)** | `--features` never invalidates the lockfile. |
| T31 | The lockfile pins the **flavor-table version and resolved interface numbers** **(user, R1)** | Deterministic TOCs across machines. |
| T32 | `build.version`: tagged release builds use `X.Y.Z` (the tag must match), untagged builds `X.Y.Z-alpha+<hash>`, and the dev profile `X.Y.Z-dev+<hash>` **(user, R1)** | |
| T33 | Publish targets have **free names plus a `type` field**. Per-target `nolib` zips are supported **(user, R1)** | Several targets per site. |
| T34 | XML references to `.wowlua` are rewritten. Modules referenced from XML stay separate files in bundled builds **(user, R1)** | |
| T35 | `asset(path)` in `wowlua:meta` folds to the full game path and checks that the file exists **(user, R1)** | |
| T36 | License header comments are never stripped. Every build gets a generated `LICENSES.txt` **(user, R1)** | Library licenses stay intact. |
| T37 | No telemetry. English messages only. `explain` works offline **(user, R1)** | |
| T38 | `dev`/`install` refuse to overwrite AddOn folders not built by wowlua unless `--force` is given. `wowlua uninstall` exists **(user, R1)** | |
| T39 | Dependencies never run code at fetch or build time. Path traversal and escaping symlinks are rejected. Tokens are stored in the OS keychain where available **(user, R1)** | |
| T40 | The wowlua runtime and standard library embedded in addons are **MIT-licensed** **(user, R1)** | Permissive. Addon authors keep any license for their own code. |
| T41 | Distribution through **GitHub Releases binaries** (plus install script and a `setup-wowlua` GitHub Action), **Homebrew, winget and Scoop** **(user, R1)** | |

| T43 | `build.flavor-files` restricts source files to flavors (glob → flavors) **(user, M0)** | Plain Lua files cannot use `@if`. `init` writes it from flavor-specific TOCs. |
| T44 | In single TOCs, a flavor that is the only targeted one of its family is written as the family name (`mainline`/`classic`) in load directives **(user, M0)** | Recognized by every client with inline directives. |
| T45 | `wowlua install` defaults to the `dev` profile **(user, M0)** | Same as `wowlua dev`, without watching. |
| T46 | Manifest schema URL: the GitHub raw URL of `schema/wowlua-<version>.json` in the repository **(user, M0)** | Works without a website. |
| T47 | M0 accepts `.wowlua` files that are pure Lua 5.1. M0 includes a release pipeline to GitHub Releases. M0 creates only the crates it needs **(user, M0)** | |
| T48 | Releases are built by a hand-written GitHub Actions workflow (six targets, checksums, install scripts) instead of cargo-dist. `setup-wowlua` is a composite action inside the wowlua repository **(proposal, M0)** | Transparent and easy to extend with Homebrew, winget and Scoop. No separate `wowlua` GitHub organization is needed. |
| T49 | A file matched by several `build.flavor-files` globs belongs to the union of their flavors **(proposal, M0)** | Predictable, order-independent. |
| T50 | `addon.flavor-overrides` expresses per-flavor metadata (title, notes, author, category, group, icon, `toc-extra`). `null` removes a field for a flavor **(user, ElvUI test)** | Real addons (ElvUI) vary titles, icons and compartment entries per flavor. One TOC can do this with inline conditions on `##` lines. |
| T51 | The package manager supports **SVN** sources, locked to a revision, using the system `svn` client **(user, ElvUI test)** | Ace3, LibStub and other core libraries are published on CurseForge's SVN repositories. `.pkgmeta` projects convert without manual work. |
| T52 | `Bindings.xml` / `Bindings_<Suffix>.xml` in the package root are passed through to the AddOn root **(user, ElvUI test)** | The client loads them automatically; dropping them loses keybindings. |
| T53 | `wowlua init` determines, per flavor, the one TOC that flavor's client reads (game suffix, then family suffix, then the plain name) and takes files, dependencies and metadata only from it **(proposal, ElvUI test)** | Matches the client. Combining TOCs would load files a client never loads. |
| T54 | `addon.toc-data` holds per-flavor files of verbatim `## Key: Value` lines. `init` writes them when a TOC has more than 200 `X-` directives **(proposal, corpus test)** | QuestieDB stores its database in about 100,000 TOC directives per flavor. In the manifest they made a 163 MB file; as data files the manifest is 16 KB. |
| T55 | `build.variable-files` keeps TOC lines with `[Game]`, `[Family]` and `[TextLocale]`. They are emitted verbatim when every targeted client supports file variables and expanded otherwise. Every expansion must exist (E5002) **(proposal, corpus test)** | BigWigs and DBM use them. Expansion keeps older clients working. |
| T56 | Flavor table: Cataclysm Classic 4.4.2 and the closed Wrath Classic 3.4.5 client support every TOC feature, including file variables, and recognize their own and all older game types **(proposal, corpus test)** | BigWigs and DBM ship single TOCs with these features for both clients. The earlier data was too conservative and forced per-flavor TOCs. |
| T57 | `init` takes the union of `SavedVariables` across the TOCs of all flavors and the value used by the most flavors for `Version`, load flags and publish IDs **(proposal, corpus test)** | Structural fields cannot vary per flavor (T50). The union loses no saved data; a single stub TOC, such as Questie's `Interface: 00000` file, is outvoted by the real ones. |
| T58 | Files an addon loads from another AddOn's folder (`..\Other\file.lua`): the owner's `init` moves them into its sources and ships them as `build.shared-files`; the loader lists them as `build.external-files` with their output path **(user, corpus test 2)** | TellMeWhen_Options and MythicDungeonTools_UI work this way. MDT's referenced XML includes libraries MDT itself loads, so the files must stay together in one place, owned by one package. |
| T59 | `addon.name` may be any valid folder name (no `\ / : * ? " < > \|`, no control characters, no leading or trailing space or dot) **(user, corpus test 2)** | Real addons use `!` and `+` prefixes to load first (`!RealUI_Preloads`, `!BugGrabber`). |
| T60 | When an adopted addon already has a `src` folder, `init` moves sources to `wowlua-src/` **(user, corpus test 2)** | AllTheThings has its own `src/`. Moving into it nested the files and pulled unloaded leftovers into the build. The output layout stays `src/…`. |
| T61 | XML references that differ in case from the file resolve like in the client, with warning W4310 **(user, corpus test 2)** | SpartanUI and Total RP 3 do this and work in game. |
| T62 | Inline directives may stand anywhere in a line, may be written `[Name: values]`, and also work in XML `file` attributes. `LoadOnDemand: true` counts as set **(verified in game, corpus test 2)** | Checked with a probe addon on the WoW: Forever beta client 1.60.1: the colon form and XML conditions both filter, `true` makes an addon load on demand. Total RP 3, ls_UI and ShadowedUF use these forms. |
| T63 | Dependency directives keep the manifest order; consecutive entries for the same flavors share a line **(proposal, corpus test 2)** | Grouping all unrestricted entries first reordered BetterBags' and RealUI's dependencies. The order may influence which dependency the client loads first, so the build keeps the author's order. |
| T64 | Milestone M1 compiles `.wowlua` files and erases type-only syntax (annotations, casts, generic parameters, `type`, `interface`, `declare`, `import type`, `export type`). Other wowlua syntax reports the milestone that implements it **(user, M1)** | Type annotations are useful long before the checker exists, and erasing them needs no lowering. |
| T65 | `wowlua fmt` follows StyLua's style: reflow at `line-width`, calls always parenthesized, tables `{ a = 1 }` flat or one field per line with a trailing comma, a single table or function argument (or a function as the last argument) hugs the parentheses, at most one blank line kept, `;` only before a statement starting with `(` **(user, M1)** | Familiar to WoW authors, many of whom already use StyLua. |
| T66 | The conformance corpus is a pinned list (`xtask/corpus.txt`: URL and SHA-256 per release) run by a scheduled CI job; regular CI runs the same checks on files written for the project (`tests/corpus-sample/`). The Lua 5.1 test suite is downloaded, not vendored **(user, M1)** | Hundreds of megabytes do not belong in every CI run; the Lua 5.1 tests carry no explicit license. |
| T67 | Fuzzing is done with deterministic randomized tests (random bytes, token soup, mutated samples) on stable Rust instead of `cargo-fuzz` **(user, M1)** | No nightly toolchain; failures reproduce from the seed. |
| T68 | Source maps of files shared by all flavors go to `.maps/<Addon>/<output path>.map`; only per-flavor files get a `<flavor>/` level **(user, M1)** | One map per output file. |
| T69 | XML `file` attributes, TOC lines and the type grammar accept the forms the spec's examples use: pack expansions `(A...)`, `(EventArgs<E>...)` and variadic results `-> ...any` **(proposal, M1)** | The grammar appendix lacked them while chapter 2 and the standard library use them. |
| T70 | Load order: dependencies found by usage analysis that contradict `build.load-order` give warning W1035 and the listed order wins; contradicting imports stay E1035. Guarded uses (`if X`, `X and …`, `not X`, `X ~= nil`, `type(X)`, and the uses those tests guard) do not order files. A function passed to a package function counts as called only if that function calls (or forwards) the parameter. The deferred-API markers are a curated list in the flavor table; `X.Name(…)` matches the method markers like `X:Name(…)` **(user, M2 corpus test)** | Without types the analysis over-approximates; `init` copies the order of a working TOC, so a migrated addon must keep it. On the corpus (108 addons) every migrated addon keeps its order. |
| T71 | Only conditions that read a `wowlua:meta` value or a `const` are static (simplified and eliminated); literal-only conditions such as `if true then` are emitted as written **(user, M2)** | Plain Lua must round-trip to identical bytecode (§13.5.3). |
| T72 | E1014 only for cycles of load-time edges. A run-time import edge constrains the order unless it lies in a cycle of the full graph; then the binding becomes lazy **(user, M2)** | Mixed cycles are common (a module calls back into its importer later) and work with lazy bindings. |
| T73 | Load-order details: W1033 is not reported for files listed in `build.load-order`; files outside a flavor take no part in that flavor's analysis; usage edges between an XML file and the files it loads are ignored (they interleave in document order) **(proposal, M2)** | The listed order already decides; flavor-specific files never load together. |
| T74 | Smaller M2 rules: destructuring without a value is error E0101; decorator names may be keywords (`@if`); when flavors need incompatible orders the build falls back to per-flavor TOCs (W4304, E1036 if `single` is forced); in shared flavor mode `addon.interface` is chosen at run time from `WOW_PROJECT_ID`; `build.minify` and `build.bundled` report `"none"`/`false` until those features exist **(proposal, M2)** | Gaps found while implementing M2. |
| T75 | Class, enum and decorator checks that need only declarations run in M3, with classes collected package-wide across imports (E3001–E3005, E3007, E3010, E3011, E3040–E3043, E3002, E3020, E3021, E3032, E3033); type-based checks (E3006, E2003 on instances, E2052, E3044, W3021) wait for the checker (M4) **(user, M3)** | Most class mistakes are structural and cheap to report early. |
| T76 | Every top-level class and enum is hoisted to a local at the module top, exported or not; use while loading before the declaration has run is E1037 **(user, M3)** | Code above a declaration must not silently read a global of the same name. |
| T77 | Native widget types come from a compiler-provided declaration file (`@widget declare class Frame`, `Button`, … for every `CreateFrame` type, `wowlua-stdlib`), implicitly in scope until the generated `wow-api` packages (M4) declare them **(user, M3)** | Widget classes need to know their native base before types exist. |
| T78 | The debugging core decorators (`@profile`, `@noprofile`, `@trace`, `@reflect`, `@checked`, `@unchecked`) report milestone M5 until then; `@inline` and `@nocheck` are accepted as no-ops until M7 and M4 **(user, M3)** | Same rule as other features of later milestones (T64). |
| T79 | M3 ships the standard-library infrastructure without public modules: `wowlua:<name>` resolves to a compiler-provided module compiled into the addon as `wowlua/std/<name>.lua` when imported (transitively; module ID `wowlua:<name>`). A module's declaration file binds exports to `@intrinsic` ids; wrapping framework decorators apply like user decorators, registering ones are called as `decorator(final, ctx)` after every transformation (`__wl.register`). `WOWLUA_STDLIB_DIR` points the compiler at a directory of modules for developing the standard library; `internal.wrap` and `internal.register` are the infrastructure's own test intrinsics **(user + proposal, M3)** | Later milestones (M5, M8) only add modules and table entries. |
| T80 | The UI sample addon lives in `examples/widget-demo`; CI builds it and runs it in the embedded VM against a mock frame API **(user, M3)** | The exit criterion (works in game) stays checkable without a client. |
| T81 | Smaller M3 rules: implementing an abstract method needs `override`; `@debugOnly` methods become no-op stubs in release builds (calls through `obj:m()` cannot be found without types); exported enums always get their table until tree-shaking arrives (M7); in a class extending a native widget directly, `super:m()` calls the native method (`getmetatable(self).__index.m`); constant parts of interpolated strings (literals, `const`s, `wowlua:meta` scalars, enum members) are folded into the text; a user decorator's context `name` is the member name for class members; statements sharing an output line are separated by a space **(proposal, M3)** | Gaps found while implementing M3. |
| T82 | `@script(name, { hook? })` is a core decorator for instance methods of widget classes: the method becomes the frame's handler of that script (`SetScript`, or `HookScript` with `hook = true`), installed after the most-derived constructor (for XML frames: before the class's `OnLoad`); registrations are inherited **(user, M3)** | Script handlers are part of the widget-class construction the compiler generates, so the decorator cannot be a library function; core decorators also work before the standard library ships. |
| T83 | The `wow-api-<flavor>` declarations are embedded in the compiler (crate `wowlua-api`, generated files committed) and regenerated with `cargo xtask types fetch` and `cargo xtask types gen`: Blizzard's API documentation from wow-ui-source at the newest live client tag of each flavor (test clients excluded), merged with Ketho's vscode-wow-api annotations at a pinned commit. Blizzard's documentation wins where both declare a name. The types packages, `flavors.<id>.types` and `wowlua types sync` arrive with the package manager; until then a compiler release updates the API **(user, M4)** | Checking works offline and without a registry, and one compiler release has one consistent API. |
| T84 | The globals of Blizzard's UI code are declared, loosely typed: top-level functions, tables, mixins and values of the FrameXML Lua files, named frames, regions and fonts of its XML files, and the client's global strings (BlizzardInterfaceResources). Names every flavor has go into the shared file **(user, M4)** | Addons use them constantly; reporting them as undeclared would bury real problems. |
| T85 | Per-flavor availability comes from the client's GlobalAPI names (BlizzardInterfaceResources, names only): a function is declared for a flavor only when its client has it. Other flavors' documentation fills gaps in older documentation, and API functions no source documents are declared untyped (`(...any) -> ...any`) **(user, M4)** | Accurate flavor guards (E2030) without losing functions older documentation lacks, such as vanilla's `GetTime`. |
| T86 | The compiler declares `LibStub` as `LibStubLibrary & ((major: string, silent: boolean?) -> any)` **(user, M4)** | Nearly every addon embeds it. |
| T87 | Basic-mode leniency, found by checking the corpus: globals assigned by any file of the package can be read (the assignment stays W1002); files calling `setfenv` get no global diagnostics; declared native classes and widgets are open (`[string]: any`), since addons store fields on frames; fields of open tables not yet assigned read as `any`; forward-declared locals read as `any` inside closures; a string literal matches an all-uppercase literal type in any casing (`"topleft"` for `"TOPLEFT"`); `..` is checked per union member; a function without any annotation is unannotated (W2055 instead of E2006) | Valid, common Lua must check without errors (M4 exit criterion). |

## Standard library

| # | Decision | Rationale |
|---|----------|-----------|
| S1 | `wowlua:saved` uses **lazy deep defaults** (AceDB-style). Stripping at logout is recursive **(user, R1)** | Nested writes persist, and files stay small. |
| S2 | Addon-internal messages are declared with **`declare message`**. `send` accepts only messages, and only WoW events are registered with the game **(user, R1)** | |
| S3 | Accessing saved data before load is **always an error**. Stdlib phase work runs first on load and last on logout **(user, R1)** | Writes would otherwise be silently lost. |
| S4 | Addon Compartment through `AddonCompartmentFrame:RegisterAddon` at runtime. Minimap button through LibDBIcon if it is loaded at login, otherwise a built-in `<Addon>MinimapButton`, never both **(user, R1)** | No globals, no TOC directives, works with button managers. |
| S5 | `wowlua:mock` is a **stdlib module**. Project mocks go in `tests/mocks/` **(user, R1)** | Always compatible with the compiler. |
| S6 | `wowlua:comm` uses **ChatThrottleLib** when loaded, otherwise a built-in conservative throttle. Versioned wire format **(user, R1)** | Shared bandwidth across addons. |
| S7 | Tests load the **whole addon** in load order and fire `ADDON_LOADED` and `PLAYER_LOGIN` before tests, unless opted out **(user, R1)** | Matches the game. |
| S8 | `@hook(target, name, { addon = "…" })` defers until a load-on-demand addon loads. `onAddonLoaded(name, fn)` helper **(user, R1)** | |
| S9 | Timers return **native C_Timer handles** **(user, R1)** | No extra allocation. |
| S10 | New stdlib modules: keybindings, tooltip hooks, movable frames, a uniform error policy, unit/aura/spell helpers, colors, SharedMedia interop, item/spell data cache, callback registry, background jobs, dialogs, menus and lists **(user, R1)** | |
| S11 | Dialogs get named frames `<Addon>Dialog<N>` registered in `UISpecialFrames`, so Escape closes them **(user, R1)** | Standard WoW mechanism, works in combat. |
| S12 | Public callback APIs are exposed through `@global` **(user, R1)** | Works on every client and for plain-Lua consumers. |
| S13 | Saved-data helpers only through `saved.handle(db)`, never on the data table **(user, R1)** | User keys never clash with helpers. |
| S14 | On downgrade, newer saved data is kept unchanged, stripping is paused, and one warning is logged **(user, R1)** | Nothing is lost if the user upgrades again. |
| S15 | No automatic `/<addon> config` command. Settings are opened through an explicit slash router entry **(user, R1)** | No unexpected globals. |
| S16 | `wowlua:comm` supports an optional AceComm-compatible wire format per channel **(user, R1)** | Addons migrating from Ace3 stay compatible with their older versions. |
| S17 | Standard-library widgets that ship inside addons (`wowlua:dialog`, the fallback frame of `wowlua:menu`, the built-in minimap button of `wowlua:launcher`) look like the client's own UI by default, built from client templates and font objects, and carry no wowlua branding **(user, M8)** | They appear in other people's addons, in front of players. |
| S18 | Those widgets are restyled by one optional `WidgetTheme` per addon (fonts, colors, border, padding, flat or template buttons), set with `dialog.setTheme`, `menu.setTheme` and `launcher.register({ theme })` / `launcher.setTheme` **(proposal, M8)** | Authors match their addon's look without forking the modules. |
| S19 | `wowlua:bindings` generates one `Bindings.xml` with every flavor's bindings in every TOC layout, not `Bindings_<Suffix>.xml` per flavor **(user, M8)** | It works on every client; a binding `@if` removed on a flavor does nothing there. |
| S20 | A binding's `default` key is emitted only for clients whose flavor table declares `binding-defaults`; none does until verified in game (W8354) **(user, M8)** | It is unverified that any client honors `default` on addon bindings. |
| S21 | Generated bindings are grouped by header: headerless first, then each header's bindings in order of first use, the attribute on the first of each group **(user, M8)** | Repeated header attributes show as repeated rows, and bindings after a header group would fall under it. |
| S22 | `wowlua:tooltip` takes its kinds and the flavors with the tooltip data system from each flavor's API declarations (`Enum.TooltipDataType`, `C_TooltipInfo`), not from hand-kept flavor-table entries **(user, M8)** | One source of truth, updated with the client dumps. |
| S23 | `wowlua:frames` anchors a saved position at the screen third the frame sits in (LibWindow-style), not always at `CENTER` or wherever the client anchored it **(user, M8)** | Frames near an edge stay there across resolution and UI-scale changes, and resizing grows away from that edge. |
| S24 | A locked movable frame cannot be moved, resized or scaled with the mouse, and its built-in grip is hidden **(user, M8)** | "Locked" means the layout cannot change by accident. |
| S25 | One mouse-wheel notch changes a movable frame's scale by 0.05 **(user, M8)** | Fine steps within the default 0.5–2 range. |
| S26 | A `wowlua:secret` module holds the secret-value helpers (`known`, `flag`, `amount`, `isSecret`, `abbreviate`) addons otherwise rewrite per file; `wowlua:aura` reads are guarded (`aura.readable`) and it wraps the engine's aura containers (`aura.container`), the only way to show auras in combat on clients with secret auras **(user, M8)** | On WoW: Forever and retail 12.x every addon aura read errors in combat, health and power are secret even out of combat, and yes/no unit queries can be secret booleans (SuuUI's client probes). |
| S27 | Aura filter words come from each flavor's `AuraUtil.AuraFilters`, extracted by the types generator into a per-flavor `AuraFilterWord` type; a flavor without the table takes the words every other flavor has **(user, M8)** | One source of truth from the client, like S22; the classic flavors lack `!` negation and several retail words. |
| S28 | `aura.container`'s default button looks like the client's buffs: icon, stack count bottom right, the engine's duration text below, debuff-type border on harmful auras **(user, M8)** | Follows S17: stdlib widgets look like the client's own UI. |
| S29 | `wowlua:dialog` looks like the client's popups: `confirm`/`prompt` at the top center like `StaticPopup1`, `export`/`import` a larger centered dialog with a scrolling text box **(user, M8)** | Follows S17. |
| S30 | `wowlua:menu` wraps `MenuUtil` and `wowlua:list` the ScrollBox list API on every flavor, without the planned fallback menu frame and faux-scroll list; menus are therefore not themed **(user, M8)** | Every supported client (all seven flavors) has both; the fallbacks would be dead code. They can return if an older client is targeted. |
| S31 | A theme restyles the built-in minimap button by tinting (border → ring, background → disc); `button = "flat"` swaps the ring for a round disc with a thin round border **(user, M8)** | Keeps the button round on any minimap shape; without a theme it stays the client's look (S17). |
| S32 | `wowlua:format` uses the client's localized formatters and strings, not fixed English short forms; `abbreviate` moved there from `wowlua:secret` **(user, M8)** | Output matches the player's language like the rest of the UI. |
| S33 | `wowlua:version` only reports a newer version through `onNewer` and prints nothing itself; every addon using it records its version in the shared `WowluaVersions` table, so any addon can query the installed versions **(user, M8)** | What the player sees is the addon's choice; one shared table needs no extra protocol. |
| S34 | `unit.roster` starts on first use, coalesces roster events (0.2 s) and keeps members whose GUID turns secret; `@bucket`/`onBucket` count by first argument and by event, firing `interval` seconds after a burst's first event like AceBucket; `launcher.dataSource` waits for LibDataBroker to arrive with any addon | Small details of the S4 recommendations the user approved; they follow AceBucket and the existing launcher's LibStub probing. |
| S35 | `wowlua:secure`: `visibility` and `state` defer driver changes in combat through `wowlua:combat`; `state` reports values by hooking `OnAttributeChanged`; the condition names checked at compile time are the client's documented macro conditions (one list for every flavor, since the client parses them in C), and their arguments are not checked; `evaluate` wraps `SecureCmdOptionParse` **(user, M8: driver plus compile-time check)** | The client offers no list of conditions to extract; one list avoids false errors from flavor differences. |
| S36 | Edit Mode on `frames.movable` (`editMode = { label, lock? }`) uses the client's selection overlay with its own scripts, saves positions when a drag ends (like LibEditMode, not with Edit Mode's Save), keys them by the active layout's name with the last saved position as the fallback, and is ignored on clients without Edit Mode **(user, M8: overlay, per-layout positions, locked outside unless `lock = false`)** | Edit Mode's save/revert covers only Blizzard's systems; LibEditMode, which addons know, saves at once. |
| S37 | The Lua environment follows an in-game probe of WoW: Forever and Ketho's annotations: `os` is not declared on any flavor, and reading it names the replacements; `bit.tobit`, `bit.tohex`, `coroutine.isyieldable` and `math.randomseed` are not declared; the client's additions to `string`, `table` and `math` are declared on every flavor, signatures from warcraft.wiki and Blizzard's calls; return types confirmed by a second probe (`freeze` returns the table, `removevalue` the number removed, `removeunordered` the removed value); the obsolete `string.gfind` and `table.setn`, which raise errors, are not **(user, M8: remove `os` with a hint; additions on all flavors)** | `format.date` crashed in game on `os.date`; the probe showed the declarations were wrong both ways. |
| S38 | WoW raises on `x / 0` and `x % 0` (probed on WoW: Forever; classic clients unprobed): a literal zero divisor (or a `const` of it) is warning W2060 on every flavor and in every mode, the spec documents WoW's arithmetic (also `math.sqrt`/`math.log` of negatives and `%d` of infinity raise), and NaN is made as `math.huge - math.huge` **(user, M8: warn on all flavors)** | `wowlua:serialize` decoded NaN with `0 / 0`; a literal zero divisor is never needed. |
| S39 | `a and nil or b` and `a and false or b` (parentheses alike) are warning W2061 in every mode: the `or` always takes over, so the result is always `b` **(proposal, M9)** | SuuUI's world map tooltips meant "no gap under a subtitle" with `gap = tip.subtitle and nil or GAP` and always got the gap; Lua's `and`/`or` choice cannot give a falsy middle value, and nothing flagged it. |
| S40 | A `local function` whose every `return` gives a fixed number of values gives at most the largest of them, counted from its body whatever its declared results (`...any` included); a name past that count in a `local` or an assignment ending in its call, or `select(n, …)` with a literal `n` past it, is warning W2062 in every mode. Only local functions (their bodies are seen); a local assigned again loses its count; a name starting with `_` is skipped, as for W1003 (wowlua's in-game suite binds `local _containers = containerTests()` only to put `@if` on it) **(proposal, M9)** | SuuUI's `call(fn, ...)` helpers, declared `...any`, returned at most 8 values through `local ok, a, …, h = pcall(fn, ...)`: Raid Info read `GetSavedInstanceInfo`'s 12 and the merchant `select(11, …)` of `GetItemInfo`, always `nil`, and no check saw it. API declarations are left out: some are incomplete (`GetCursorInfo` declares no results), so their counts could be wrong. |
